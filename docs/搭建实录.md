# 大促需求收集平台 — 搭建实录

> 本文档记录「大促需求收集平台」从零到上线的完整搭建历程，按时间线梳理每个阶段做了什么、为什么这样做、遇到了什么问题以及如何解决。
>
> 与 [应用介绍文档](./应用介绍文档.md) 互补：介绍文档讲「应用是什么」，搭建实录讲「怎么一步步搭出来的」。

---

## 一、项目概述

| 项目 | 信息 |
|------|------|
| 应用名称 | 大促需求收集平台 |
| 定位 | 企业内部多工具需求的结构化收集 → AI 智能整合 → 优先级评分 → 飞书通知跟进的全链路管理平台 |
| 搭建周期 | 2026-06-24 ~ 2026-07-14（约 3 周） |
| 部署平台 | 妙搭全栈应用平台（FaaS） |

### 核心价值

大促活动前，各业务团队对内部工具产生大量功能需求。这些需求以往散落在群聊、文档、口头沟通中，难以追溯、重复度高、优先级模糊。本平台旨在提供：

- **结构化收集**：按「板块 → 栏目」组织需求，全员通过统一富文本入口提交
- **AI 智能整合**：自动识别相似需求并合并，避免重复开发
- **量化优先级**：多维度自动评分 + 百分位排名，辅助管理员决策
- **透明化跟进**：飞书消息自动通知，状态变更实时触达

## 二、技术选型

| 层级 | 技术 | 选型理由 |
|------|------|---------|
| 前端框架 | React 19 + TypeScript | 组件化开发，类型安全 |
| 样式 | Tailwind CSS + shadcn/ui | 语义化 token，快速还原设计稿 |
| 表格 | Ant Design Table（antd-table） | 高密度数据展示，支持固定列、内联编辑 |
| 富文本 | Tiptap 编辑器 | 支持图文混排，编辑与只读渲染统一 |
| 后端框架 | NestJS 10 + TypeScript | 模块化架构，依赖注入 |
| ORM | Drizzle ORM | 类型安全的 PostgreSQL 操作 |
| 数据库 | PostgreSQL | 关系型存储 + JSONB 动态字段 |
| AI 能力 | 飞书插件（AI 文本生成） | 需求合并分析，流式输出 |
| 通知能力 | 飞书插件（消息发送） | 卡片消息 + 交互按钮跳转 |
| 部署 | 妙搭全栈应用平台 | 前后端一体部署，自动热重载 |

## 三、搭建历程

### 阶段一：基础骨架与需求提交闭环（6/24）

**目标**：从零搭建应用骨架，跑通"创建栏目 → 提交需求 → 浏览需求"的核心闭环。

**完成事项**：

1. **初始化布局主题与占位路由**
   - 基于妙搭模板初始化项目，配置 Tailwind 主题色系（品牌蓝 #2563EB + 语义绿/橙）
   - 搭建顶部操作栏（应用名 + 导航 + 当前用户下拉）和居中容器布局
   - 创建占位路由：栏目列表、需求广场、需求详情

2. **搭建需求模块架构与共享类型**
   - 在 `shared/api.interface.ts` 定义前后端共享的类型契约
   - 创建后端 NestJS 模块：`demand`（需求）、`demand-category`（栏目）、`merged-demand`（整合）
   - 确立 Controller-Service 分层模式

3. **创建数据库表**
   - `demand_category`：栏目表（名称、描述、启用状态、部门选项）
   - `demand`：需求主表（标题、富文本背景、部门、创建人、状态等）
   - `demand_comment`：评论表
   - `merged_demand` + `merged_demand_source`：整合需求及关联表

4. **实现需求提交、投票、评论前后端功能**
   - 栏目列表页展示卡片网格
   - 需求广场页卡片网格 + 无限滚动加载
   - 提交需求弹窗（富文本编辑器 + 部门选择）
   - 需求详情页 + 评论区
   - 投票与评论功能

5. **AI 需求整合与管理表格首版**
   - 创建 AI 合并分析插件实例 `demand_merge_analyzer`
   - 实现整合需求表格，展示原始需求与整合需求

6. **聚焦主线：移除投票功能**
   - 评估后发现投票功能偏离核心需求收集主线，移除以保持产品聚焦
   - 新增原始需求图片字段，保留富文本附件能力

**关键决策**：
- 选择「栏目」作为需求组织的基本单元，对应一个工具或一类工具
- 前后端共享类型集中在 `shared/api.interface.ts`，确保接口契约一致

### 阶段二：需求整合体验打磨（6/25）

**目标**：打磨需求整合的用户体验，统一表格视图，精简表单字段。

**完成事项**：

1. **重构为单表交互**
   - 将原始需求与整合需求合并到同一表格视图，按分数降序排列
   - 管理员无需在两个视图间切换，降低认知负担
   - 清理废弃的独立整合页组件

2. **实现工具需求栏目分层管理**
   - 栏目支持启用/停用，停用后普通用户不可见
   - 管理员可在管理态查看和操作停用栏目

3. **表单字段精简（多轮迭代）**
   - 移除预期价值、期望上线时间字段的展示（详情页与表单同步精简）
   - 合并标题与背景为单一富文本字段，系统自动截取前 50 字作为标题
   - 移除独立的标题输入框，降低用户填写负担
   - 将 `expected_value` 数据库字段改为可选

   > **决策背景**：初期表单字段过多，用户填写负担重。通过多轮精简，最终保留"需求内容（富文本）+ 部门 + 类型 + 优先级 + 阻塞"的核心字段，将价值评估字段后置到打分阶段。

4. **附件图片展示优化**
   - 整合表格列标题改为「需求内容」
   - 从富文本背景中提取图片 URL，展示缩略图
   - 需求详情页以只读模式渲染富文本，保留图片和格式
   - 附件列直接展示图片缩略图，点击弹窗放大
   - 关联原始需求也展示附件图片缩略图

**遇到的问题**：
- 富文本中图片 URL 提取的正则需要处理单引号和双引号两种情况
- 缩略图位置需要与表格附件列对齐，经过多轮微调

### 阶段三：部门配置与飞书通知（6/26）

**目标**：支持栏目自定义部门选项，实现新需求飞书通知与 AI 合并建议。

**完成事项**：

1. **栏目自定义提交部门**
   - 管理员在栏目编辑中配置可选的「提出部门」列表
   - 用户提交需求时，部门下拉来源为所在栏目配置
   - 栏目未配置时回退到内置默认部门列表
   - 调整部门下拉宽度与标签对齐

2. **实现新需求飞书通知**
   - 创建自动化任务触发器 `demand_created_notify`（record_change 类型，监听 `demand` 表 INSERT）
   - 创建飞书消息发送插件实例 `demand_submit_feishu_notify_1`
   - 通知流程：新需求提交 → 读取同栏目原始+整合需求 → AI 分析可合并性 → 查询 demand_admin 角色成员 → 发送飞书卡片消息（含栏目名、需求标题、部门、提交人、AI 合并建议、跳转按钮）
   - 通知全程异常不阻塞需求提交本身

3. **诊断与调试**
   - 增强飞书通知诊断日志，定位发送链路问题
   - 完成诊断版本发布部署，验证线上通知触发

**遇到的问题**：
- 飞书通知初次实现时存在发送失败，需要增强日志定位根因
- AI 合并建议的提示词需要调优，确保输出可操作的 JSON 格式

**关键决策**：
- 通知逻辑放在自动化任务（record_change 触发器）中异步执行，不阻塞用户提交需求的主流程
- AI 分析复用 `demand_merge_analyzer` 插件实例，对单条新需求做可合并性分析

### 阶段五：重要度打分体系（7/1–7/3）

**目标**：建立需求价值量化评分体系，辅助管理员判断优先级，并实现状态跟进通知。

**完成事项**：

1. **开放评分字段**
   - 开放需求表单中的预期价值类型（GMV 提升 / 工作效率提升）
   - GMV 类型：按量级 1~5 分（10 万以下 ~ 500 万以上）
   - 效率类型：按影响人数 + 节省时长各 1~5 分求和（1~10 分）

2. **实现需求重要度打分标签（初版）**
   - 多维度加权自动评分：预期价值 + 上线紧迫度 + 需求类型 + 阻塞性 + 优先级
   - 初版采用固定阈值：≥18 分红色「高」、9~18 分黄色「中」、<9 分绿色「低」
   - 整合需求得分 = 关联原始需求平均分 + 关联数量

3. **整合界面按得分降序排序**
   - 表格按最终得分降序排列，高价值需求置顶

4. **实现需求跟进中飞书通知**
   - 创建触发器 `demand_status_followup_notify`（监听 `demand` 表状态更新为「跟进中」）
   - 创建触发器 `merged_demand_status_followup_notify`（监听 `merged_demand` 表状态更新）
   - 通知对象：原始需求创建者，或整合需求下全部原始需求创建者
   - 通知内容：需求标题、负责人、预计排期，附带跳转至「我的需求」按钮

5. **新增「我的需求」页**
   - 用户可查看自己提交过的全部需求
   - 卡片网格展示，含状态标识
   - 支持跳转至需求详情页

6. **需求迭代：改为百分位分数标签**
   - **背景**：固定阈值（18/9）无法适应不同需求批次的数据分布——需求少时几乎全是「低」，需求多时「高」标签泛滥
   - **改为**：按全部需求得分排名的百分位分级
     - 前 10%（`floor(总数 × 0.1)`，至少 1 个）→ 红色标签
     - 前 20%（前 10% 之后）→ 黄色标签
     - 其余 → 绿色标签
   - 标签内容直接显示得分值（整数，向下取整），不再显示「高/中/低」文字

7. **手动调分功能**
   - 新增 `PATCH /api/demands/:id/score` 接口（管理员权限）
   - 整合需求通过 `PUT /api/merged-demands/:id` 的 `manualScore` 字段更新
   - 数据库 `demand` 和 `merged_demand` 表各新增 `manual_score` 列
   - 管理员点击重要度标签可输入得分覆盖自动计算值，影响排序与着色
   - 支持重置回自动计算分

8. **排期与通知优化**
   - 整合页新增预计排期列
   - 修复整合需求预计排期列不显示的问题

**关键决策**：
- 得分计算采用「前端实时计算 + 后端持久化手动覆盖」双轨制：无手动分时按公式自动计算，有手动分时优先使用手动分
- 百分位分级取代固定阈值，适应不同批次需求数量，确保高优先级标签始终稀缺有意义
- 手动调分入口仅管理员可见，与表格已有的内联编辑模式（状态/负责人/反馈）保持一致

### 阶段七：板块体系与权限分割（7/10–7/14）

**目标**：引入「板块」分层组织需求，实现内容场动态表单，完善板块级权限隔离。

**完成事项**：

1. **修改应用名称**
   - 应用名称从「企业需求收集与整合系统」改为「大促需求收集平台」，更贴合实际使用场景

2. **需求广场板块选择**
   - 预置 4 个板块：货品规则、消费券、内容场、大促运营工具包
   - 首页先展示板块卡片，选择板块后展示该板块下栏目
   - 管理员在栏目编辑中选择所属板块
   - 整合页同样支持板块筛选
   - 移除栏目表单中的板块选择器（改为在栏目管理中配置）

3. **内容场自定义表单字段**
   - 管理员通过表单字段编辑器配置 `form_fields`（JSONB）
   - 支持 6 种字段类型：单行文本、多行文本、日期、链接、图片、下拉单选
   - 用户提交时根据 `form_fields` 动态渲染表单
   - 标题自动取第一个文本字段前 50 字符
   - 需求详情页和整合表格根据 `form_fields` 展示自定义字段值
   - 仅 `section === '内容场'` 且 `formFields` 非空时生效，其他板块保留原有硬编码表单

4. **板块管理员权限分割**
   - 实现按板块隔离的管理权限
   - 完善板块权限过滤与校验
   - 我的需求页展示来源板块标签

5. **体验修复**
   - 用 URL 参数持久化板块选择状态（刷新/分享链接保持板块上下文）
   - 修复回退跨级跳转问题
   - 修复图片显示使用正确下载 URL
   - 移除我的需求页部门展示（精简信息）

**关键决策**：
- 采用「板块 + 栏目」两层分类：板块做大场景分组（4 个大促场景），栏目做工具维度细分
- 内容场动态表单通过 `form_fields` JSONB 配置驱动，避免为每个栏目硬编码表单；其他板块完全保留原有硬编码表单，避免过度抽象
- URL 参数持久化板块选择，确保分享链接和刷新行为一致

## 四、核心架构设计

### 4.1 页面路由与角色

| 路由 | 页面 | 可见角色 |
|------|------|---------|
| `/` | 栏目入口（板块选择 → 栏目卡片） | 全员 |
| `/category/:categoryId` | 需求广场（卡片网格 + 滚动加载） | 全员 |
| `/demand/:id` | 需求详情（正文 + 评论区） | 全员 |
| `/my-demands` | 我的需求（个人提交记录） | 登录用户 |
| `/merged-demands` | 整合栏目列表（板块 → 栏目选择） | demand_admin |
| `/merged-demands/:categoryId` | 需求整合（统一表格 + 手动/AI 整合） | demand_admin |

### 4.2 数据模型

| 表 | 用途 | 关键字段 |
|------|------|---------|
| `demand_category` | 栏目 | name, description, enabled, departments, section, form_fields |
| `demand` | 需求主表 | category_id, title, background, department, creator, status, gmv_level, efficiency_*, manual_score, custom_fields |
| `demand_comment` | 评论 | demand_id, user_id, content |
| `merged_demand` | 整合需求 | category_id, title, reason, status, assignee, manual_score, planned_schedule |
| `merged_demand_source` | 整合关联 | merged_demand_id, demand_id |

### 4.3 AI 能力（插件实例）

| 插件实例 | 基础插件 | 用途 |
|---------|---------|------|
| `demand_merge_analyzer` | AI 文本生成（stream） | 需求合并分析：前端 AI 整合对话框批量分析 + 后端单条新需求可合并性分析 |
| `demand_submit_feishu_notify_1` | 飞书消息发送 | 发送飞书卡片消息，含交互按钮跳转 |

### 4.4 自动化任务

| 触发器 | 类型 | 监听表 | 通知对象 | 说明 |
|--------|------|--------|---------|------|
| `demand_created_notify` | record_change (INSERT) | demand | demand_admin 全员 | 新需求提交 → AI 合并建议 → 飞书卡片通知 |
| `demand_status_followup_notify` | record_change (UPDATE) | demand | 需求创建者 | 状态变更为「跟进中」→ 飞书通知提交人 |
| `merged_demand_status_followup_notify` | record_change (UPDATE) | merged_demand | 关联原始需求创建者 | 整合需求状态变更为「跟进中」→ 飞书通知 |

### 4.5 权限体系

- **普通用户**：浏览栏目、提交需求、查看详情、发表评论、查看自己的需求
- **需求管理员（demand_admin）**：额外拥有栏目管理、需求整合（手动/AI）、分数调整、查看全部栏目权限
- 板块管理员权限分割：按板块隔离管理权限
- 前后端双层鉴权：后端 `@CanRole(['demand_admin'])` 装饰器 + 前端 `useAuth` Hook + `<CanRole>` 组件包裹

## 五、关键设计决策与经验总结

### 5.1 单表交互统一视图

将原始需求与整合需求放在同一表格中按分数降序排列，管理员无需在两个视图间切换。这一决策在阶段二确立后贯穿后续所有迭代，降低了管理员的认知负担。

### 5.2 得分计算的双轨制

- **自动计算**（前端实时）：多维度加权公式，无需持久化，需求字段变更即时生效
- **手动覆盖**（后端持久化）：管理员可手动指定得分，优先于自动计算

这一设计兼顾了自动化与灵活性：大部分需求由公式自动评分，少数需要人工干预的需求通过手动分覆盖，且手动分持久化后刷新仍生效。

### 5.3 百分位分级取代固定阈值

初版采用固定阈值（≥18 高 / 9-18 中 / <9 低），但实际使用中发现：
- 需求少时几乎全是「低」标签
- 需求多时「高」标签泛滥

改为百分位分级（前 10% 红 / 前 20% 黄 / 其余绿）后，高优先级标签始终稀缺有意义，适应不同批次需求数量。

### 5.4 自动化任务做异步通知

新需求通知和状态跟进通知均通过 record_change 触发器异步执行，不阻塞需求提交/状态更新的主流程。通知逻辑全程异常捕获，即使通知发送失败也不影响业务操作。

### 5.5 板块 + 栏目两层分类

- **板块**（section）：预置 4 个大促场景，做大场景分组
- **栏目**：做工具维度细分，管理员可创建/编辑/启停

首页先展示板块卡片，选择板块后展示栏目，层级清晰。板块选择通过 URL 参数持久化，确保刷新和分享链接行为一致。

### 5.6 内容场动态表单

仅「内容场」板块的栏目支持通过 `form_fields` JSONB 配置自定义表单字段（6 种类型），其他板块保留原有硬编码表单。这一决策避免了为每个栏目硬编码表单的重复工作，同时不过度抽象——只在确实需要灵活配置的场景引入动态化。
